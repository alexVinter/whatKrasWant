# AGENTS.md — «Чего хочет Красноярск?»

Этот файл содержит постоянные правила для AI-агента при разработке проекта.
Он не заменяет ТЗ и документы в `docs/`, а задаёт порядок приоритетов, ограничения и рабочую дисциплину.

---

## 1. Источники истины и их приоритет

Всегда используй источники в таком порядке:

1. `docs/DECISIONS_AFTER_MEETING_актуализировано_14-08-2026.docx` — последние решения заказчика и встречи.
2. `docs/cursor_visual_refs/desktop/` — главный визуальный источник истины для desktop.
3. `docs/cursor_visual_refs/mobile/` — источник истины для адаптивного поведения и mobile.
4. `docs/Макет Десктоп (2).pdf`.
5. `docs/Макет Мобильная версия.pdf`.
6. `docs/ТЗ .docx` — применяется только в части, не изменённой более поздними решениями.

Если источники противоречат друг другу:
- используй источник с более высоким приоритетом;
- не возвращай отменённые требования из старого ТЗ;
- если после применения приоритета всё ещё остаётся неоднозначность — остановись и задай вопрос пользователю;
- ничего не додумывай самостоятельно.

## 2. Визуальная реализация

Согласованный desktop-макет — главный источник истины по внешнему виду.

Перед реализацией или изменением любого frontend-экрана:
1. открой соответствующий PNG в `docs/cursor_visual_refs/desktop/`;
2. открой соответствующий PNG в `docs/cursor_visual_refs/mobile/`;
3. сравни структуру, композицию, размеры блоков, отступы, типографику, цвета и поведение адаптива;
4. не добавляй визуальные элементы, которых нет в утверждённых материалах.

Не придумывать:
- новые блоки;
- новые кнопки;
- новые поля;
- новые страницы;
- новые секции;
- новый дизайн;
- новые UX-сценарии без отдельного решения.

Mobile — адаптивная версия того же приложения, а не отдельный продукт.

Обязательные контрольные ширины frontend:
- 360 px;
- 390 px;
- 768 px;
- 1440 px;
- 1920 px.

---

## 3. Публичная структура сайта

Публичная главная состоит из четырёх основных блоков в таком порядке:

`Проект → Карта → Рейтинг инициатив → Новости`

Не реализовывать в публичной части:
- публичные фильтры карты;
- публичные фильтры списка инициатив;
- публичный поиск инициатив;
- отдельный блок сфер/категорий на главной;
- блок стадий проекта;
- дополнительные публичные счётчики, кроме указанного ниже;
- отдельную публичную страницу результатов / top-20;
- личный кабинет жителя.

На главной под кнопкой «Предложить идею» показывается показатель:

`Количество собранных идей`

Другие публичные счётчики не выводятся.

---

## 4. Инициативы — публичное поведение

Публично для инициативы показываются:
- автор: имя / фамилия;
- название;
- описание;
- одно изображение, если оно есть;
- место / территория;
- геоточка на карте;
- количество голосов;
- кнопка «Поддержать» на детальной странице.

Публично НЕ показывать:
- внутренний `source_type`;
- `public_number`;
- внутренние ID;
- внутренний статус;
- служебные поля.

На карте:
- маркер инициативы;
- по клику — краткая карточка;
- кнопка «Подробнее»;
- переход на детальную страницу инициативы.

Полный публичный список инициатив:
- отдельная страница;
- сортировка по популярности / количеству действительных голосов;
- без публичных фильтров;
- без публичного поиска.

---

## 5. Подача инициативы жителем

Житель может отправить инициативу только после авторизации через VK ID.

Публичная форма содержит:
- имя, полученное / определённое после VK ID;
- название инициативы;
- описание инициативы;
- одно изображение;
- обязательную геоточку на карте;
- согласия / принятие необходимых документов.

Пользователь НЕ выбирает категорию.

Категорию назначает администратор после отправки.

Правила категории:
- заявка может находиться в статусе `MODERATION` без категории;
- перевод инициативы в `PUBLISHED` запрещён, если категория не назначена.

После отправки:
- показывается экран подтверждения;
- публикация не гарантируется;
- личный кабинет не создаётся;
- отслеживание статуса не предоставляется;
- пользовательские уведомления не добавляются без отдельного решения.

---

## 6. Изображения

Для одной инициативы допускается максимум одно изображение.

Для пользовательской и административной загрузки:
- JPG / JPEG / PNG;
- ограничение размера — до 10 МБ, если более поздним решением не указано иное;
- сервер проверяет MIME и сигнатуру;
- удаляет EXIF;
- создаёт оптимизированную версию и миниатюру;
- хранение — S3-совместимое.

Не реализовывать галерею и слайд-шоу инициатив.

---

## 7. VK ID и публичная авторизация

VK ID обязателен:
- для подачи инициативы;
- для голосования / кнопки «Поддержать».

Просмотр публичной части не требует авторизации.

После VK ID создаётся минимальная техническая учётная запись `User` без личного кабинета.

Пароли VK не передаются и не хранятся.
Токены VK не логируются и не попадают в экспорт.

Публичная сессия — через безопасную серверную сессию / HttpOnly Secure cookie.

Заблокированный пользователь не может:
- подавать инициативы;
- голосовать.

---

## 8. Голосование

Правила голосования:
- голосовать может только активный пользователь, авторизованный через VK ID;
- один пользователь может проголосовать за одну инициативу только один раз;
- пользователь может голосовать за любое количество разных инициатив;
- голос нельзя отменить;
- перед записью голоса показывается подтверждение;
- в рейтинге учитываются только действительные, не исключённые голоса.

На уровне БД должна быть уникальность пары:

`(idea_id, user_id)`

Антифрод:
- rate limit;
- хэш IP;
- хэш user-agent;
- частота / время действий;
- флаги аномальности;
- подозрительный голос можно исключить из рейтинга без физического удаления;
- исключение обязательно журналируется.

ВАЖНО:
- голосование непосредственно из карточки в слайдере «Рейтинг инициатив» пока НЕ реализовывать;
- в слайдере показывать изображение, автора, название и количество голосов;
- голосование выполняется на детальной странице инициативы через кнопку «Поддержать» и подтверждение;
- менять эту механику только после отдельного подтверждения заказчика.

---

## 9. Рейтинг инициатив

На главной рейтинг показывается горизонтальным слайдером.

Desktop:
- визуально соответствовать утверждённому desktop PNG.

Mobile:
- показывать основную карточку и часть следующей карточки;
- должно быть интуитивно понятно, что блок листается горизонтальным свайпом.

Кнопка «Смотреть все» у рейтинга ведёт на полный список инициатив.

Отдельная публичная страница top-20 не создаётся.
`is_top20` остаётся внутренним административным признаком.

---

## 10. Карта

Использовать:
- Leaflet;
- OSM-совместимый сменный источник тайлов;
- WGS84 для координат;
- GeoJSON-границу города для проверки допустимой точки.

Требования:
- опубликованные инициативы с геоточкой отображаются на карте;
- близкие точки могут кластеризоваться;
- у карты есть видимая атрибуция OSM / поставщика;
- публичных фильтров нет;
- карта загружается лениво;
- URL поставщика тайлов задаётся конфигурацией.

Mobile:
- карта занимает доступную ширину экрана;
- это отдельный интерактивный viewport;
- пользователь перемещает и масштабирует карту внутри блока.

Публичный `tile.openstreetmap.org` использовать только для разработки / теста, если иной поставщик ещё не утверждён.

---

## 11. Новости

Новости являются отдельной сущностью и функциональным блоком, добавленным более поздними решениями заказчика.

Администратор может:
- создавать новость;
- редактировать;
- публиковать;
- управлять её содержимым.

Публично:
- на главной новости показываются горизонтальным слайдером;
- свежие новости идут первыми;
- карточка содержит дату и название, изображение — при наличии;
- есть детальная страница новости `/news/:slug`.

Mobile:
- использовать ту же механику, что в рейтинге;
- основная карточка + видимая часть следующей.

Пока НЕ создавать самостоятельно отдельную страницу списка всех новостей `/news`, так как её макет и конечная логика не утверждены.
Кнопка «Смотреть все» у новостей не должна получать придуманную агентом целевую страницу без отдельного решения.

Не назначать новости бизнес-релизу 1 или 2 как согласованное требование, пока это отдельно не подтверждено.

---

## 12. Административная часть

Административные экраны реализуются только в пределах утверждённых макетов.

Предусмотреть:
- вход администратора;
- обзор;
- список инициатив;
- создание экспертной инициативы;
- карточку / редактирование инициативы;
- историю ревизий;
- категории и районы;
- новости;
- статистику;
- XLSX-выгрузку;
- настройки публичности;
- журнал действий.

Админ-список инициатив может содержать:
- фильтры по статусу;
- источнику;
- категории;
- территории;
- поиск по названию / автору.

Публичные ограничения на фильтры не относятся к админке.

Backend-функции управления техническими пользователями VK и блокировками предусмотреть согласно ТЗ.

ВАЖНО:
- не создавать новый отдельный экран «Пользователи», которого нет в утверждённых макетах, без отдельного решения.

---

## 13. Статусы инициатив

Использовать базовые статусы:

- `DRAFT`
- `MODERATION`
- `PUBLISHED`
- `ARCHIVED`

Пользователь публично эти статусы не видит.

Правила:
- экспертная инициатива может создаваться администратором как `DRAFT`;
- публичная заявка создаётся как `MODERATION`;
- публикация возможна только после выполнения обязательных требований;
- категория обязательна перед `PUBLISHED`;
- архивирование не должно физически удалять инициативу;
- восстановление должно быть возможно согласно ТЗ.

`is_top20` хранится отдельно от статуса.

---

## 14. История изменений и аудит

`IdeaRevision`:
- неизменяемая история редакций инициативы;
- хранит снимок данных;
- администратора;
- дату;
- причину / комментарий, если предусмотрено.

Исходная публичная заявка должна сохраняться.

`AdminAuditLog` фиксирует как минимум:
- редактирование инициатив;
- публикацию;
- снятие с публикации;
- архивирование / восстановление;
- назначение категории;
- top-20;
- изменения новостей;
- изменения настроек;
- блокировки пользователей;
- исключение подозрительных голосов.

---

## 15. Feature flags

Использовать только следующие согласованные флаги:

- `PUBLIC_CATALOG`
- `PUBLIC_SUBMISSION`
- `VOTING`
- `RESULTS`

Не вводить дополнительный флаг `RATING` без отдельной необходимости и согласования.

Флаги:
- хранятся в БД / `SystemSetting`;
- меняются администратором;
- не требуют пересборки приложения.

---

## 16. Статистика и XLSX

Публично общая статистика не выводится.

В административной части сохраняются статистика и экспорт.

XLSX должен включать предусмотренные ТЗ данные, включая листы:
- «Инициативы»;
- «Авторы и источники»;
- «Голоса»;
- «Статистика»;
- «Топ-20».

Не экспортировать:
- VK токены;
- хэши сессий;
- IP-хэши;
- user-agent-хэши;
- секреты и служебные ключи.

---

## 17. Архитектура и стек

Использовать утверждённый стек, если нет отдельного согласованного изменения.

Frontend:
- React;
- TypeScript;
- Vite;
- React Router;
- TanStack Query.

Backend:
- Node.js;
- NestJS;
- PostgreSQL 15+;
- Prisma ORM;
- REST API.

Дополнительно:
- Leaflet;
- S3-compatible storage;
- Docker Compose;
- Nginx.

Frontend и backend должны быть разделены.

Все изменения структуры БД — только через Prisma migrations.

Секреты и ключи никогда не хранить в git.

---

## 18. Безопасность

Обязательные требования:
- HTTPS во внешних соединениях;
- защита admin API на сервере;
- HttpOnly Secure cookie для административной сессии;
- стойкий хэш пароля администратора (Argon2/bcrypt);
- защита от CSRF, XSS, SQL-инъекций и перебора;
- rate limit;
- серверная валидация всех входных данных;
- безопасная загрузка файлов;
- EXIF-очистка изображений;
- секреты только через env / secret storage;
- минимизация персональных данных в логах;
- VK-токены не логировать;
- персональные данные и резервные копии должны учитывать требования ТЗ к размещению на инфраструктуре РФ.

---

## 19. Нефункциональные требования

Учитывать требования ТЗ, если они не отменены более поздними решениями:
- адаптивность 360–1920 px;
- последние стабильные Chrome / Edge / Firefox / Safari;
- русский язык;
- базовая доступность WCAG 2.1 AA;
- клавиатурная навигация и видимый focus;
- alt для изображений;
- lazy loading карты и тяжёлого контента;
- структурированные логи;
- резервное копирование;
- мониторинг;
- нагрузочные критерии из ТЗ.

---

## 20. Правила работы AI-агента

Перед любым изменением:
1. прочитай задачу пользователя;
2. найди относящиеся к ней решения в `docs/`;
3. проверь приоритет источников;
4. для frontend обязательно открой соответствующие PNG;
5. изучи существующий код до изменения;
6. меняй только относящуюся к задаче часть.

Запрещено без прямого запроса:
- массовый рефакторинг;
- смена стека;
- перенос архитектуры «заодно»;
- переименование больших частей проекта;
- новая библиотека, если задача решается существующим стеком;
- изменение соседних экранов;
- добавление «улучшений UX» от себя;
- создание новых страниц / сущностей / функций без основания в документах.

Если задача небольшая — изменения тоже должны быть небольшими.

---

## 21. Проверка после изменения

После каждого изменения по возможности выполнить относящиеся проверки:

Backend:
- typecheck;
- lint;
- unit / integration tests для изменённой логики;
- Prisma validation / migrations check;
- сборка.

Frontend:
- typecheck;
- lint;
- tests, если есть;
- production build;
- визуальная сверка с desktop/mobile PNG;
- проверка 360, 390, 768, 1440, 1920 px.

Не заявлять, что задача выполнена, если сборка или обязательные проверки падают.
Если проверить что-то невозможно — явно сказать об этом.

---

## 22. Git и размер изменений

Работать маленькими проверяемыми этапами.

Одна задача должна давать один логически завершённый результат.

Не смешивать в одном изменении:
- новую функцию;
- крупный рефакторинг;
- косметические изменения соседних экранов.

Не делать `git commit`, `git push`, merge, rebase и другие необратимые Git-действия без прямого запроса пользователя.

После выполнения перечислить:
- что сделано;
- какие файлы изменены;
- какие проверки выполнены;
- остались ли ограничения / открытые вопросы.

---

## 23. Запрещено реализовывать без отдельного решения

До отдельного подтверждения НЕ реализовывать:
- публичные фильтры карты;
- публичные фильтры инициатив;
- публичный поиск инициатив;
- личный кабинет жителя;
- выбор категории жителем;
- более одного изображения для инициативы;
- отдельную публичную страницу top-20 / результатов;
- голосование прямо из карточки рейтинга;
- отдельный новый экран управления пользователями в админке;
- отдельную страницу `/news` со списком всех новостей;
- новые публичные разделы;
- функциональность, придуманную агентом самостоятельно.

---

## 24. Открытые вопросы — не решать самостоятельно

Следующие вопросы считать открытыми до отдельного решения:
- нужна ли отдельная страница списка всех новостей и куда ведёт «Смотреть все» у новостей;
- к какому бизнес-релизу относятся новости;
- окончательная дата публичного запуска Релиза 2;
- окончательное название категории «Электронные проекты»;
- утверждённый источник GeoJSON-границы Красноярска;
- production-поставщик картографических тайлов и плательщик;
- возможность голосования непосредственно из карточки рейтинга.

Если одна из этих тем влияет на текущую задачу — остановись и задай вопрос вместо самостоятельного решения.

## 25. Главный принцип

Реализовывать именно согласованный проект «Чего хочет Красноярск?», а не «улучшенную версию по мнению агента».

Последние решения заказчика и утверждённые визуальные макеты важнее ранних противоречащих требований.

При сомнении — не додумывать, а спрашивать.
